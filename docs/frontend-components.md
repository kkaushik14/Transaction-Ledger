# Frontend component contracts

The approved v0.2 implementation follows this order: tokens and component contracts, UI primitives, shell/navigation, landing sections and domain features, then page composition. All components use monochrome tokens and semantic HTML. The user has now authorized transfer controls using the existing deployed API; microservices remain excluded.

## Transfer component contract (defined before implementation; now delivered)

| Module            | Public inputs and responsibility                                            | Required behavior                                                                                                                                                                                     |
| ----------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TransferReview    | Validated immutable command; confirmation/retry and optional edit callbacks | Readable source/destination UUIDs, exact amount, description and reference; explicit confirmation, keyboard focus, no HTTP calls                                                                      |
| TransferReceipt   | Contract-validated transfer creation result                                 | Committed transfer/leg IDs, both account UUIDs, exact amount and balances after transfer; recipient navigation; no inferred success for conflicts                                                     |
| TransferForm      | Current source UUID and authoritative refresh callback                      | Existing primitives, source fixed to route, destination UUID/amount/description validation, edit → review → confirm; explicit pending/error/uncertain/conflict/success states                         |
| useTransferIntent | Source UUID and refresh callback                                            | One in-flight request; save exact normalized payload/reference before HTTP; restore unresolved intents without auto-sending; explicit identical retries; late responses cannot erase newer references |
| transfer-intent   | Source-scoped session persistence                                           | Validate stored command and account ownership; fail before sending if persistence is unavailable; remove only a matching reference                                                                    |
| transfers.api     | Shared transfer request/response DTOs                                       | Existing HTTP client; validate response correlation with the original command, never retry automatically                                                                                              |

Review/receipt and the feature hook/form passed 24 independent component cases before AccountWorkspace integration. The workspace stacks credit/debit and transfer cards beside history on desktop and use the existing single-column mobile layout. All code folders expose explicit index.ts entries with .js imports across boundaries.

Known rejection permits editing the preserved fields. A timeout, invalid response or 5xx means outcome unknown; freeze the original command and offer only explicit identical retry plus account refresh. A duplicate refreshes reads and displays a conflict, never a success receipt. Keep the preserved intent until the user explicitly acknowledges reviewing the account before starting another transfer. On success, refetch current source balance/history (reset page 1, retain filter); recipient navigation performs its own fresh reads. Receipt balances are the snapshots returned by the committed transfer, not a cache of current balances. Read-refresh failure must not repeat a committed write.

Verification includes field validation, review-before-send, pending double-submit, reload/account-switch isolation, exact reference/payload retention, both duplicate codes, known rejection, unconfirmed results, storage failures, response mismatches, stale completion, source refresh and recipient history. Browser tests use the disposable API/database fixture, all five required widths and automated accessibility; never mutate hosted Supabase in tests.

API modules parse responses against shared contracts. Feature hooks own requests and cancellation; primitives and layout never fetch domain data. Money is never calculated as a JavaScript number. Browser session storage may retain an uncertain transaction intent for safe retry; it never stores database credentials or authoritative balances. A known account name originates from account creation and may be retained with the tab selection; otherwise the header uses Account and Account ID.

Every source folder now exposes an explicit `index.ts` entry, consumed through `.js` specifiers. Pages and other domain features use feature facades; implementation files use owned components/hooks entries across subfolders and direct sibling imports within a folder. Transaction-intent storage helpers stay below the transaction facade. `src/index.ts` exports `App` without mounting it or installing CSS; `main.tsx` owns both DOM mounting and the single `styles/index.ts` import. No additional UI abstractions or feature behavior were introduced by this boundary refactor.

Meaningful component behavior is verified independently before pages are assembled. Final checks include keyboard navigation, dialog focus, reduced motion, live API flows in an isolated database, automated accessibility checks, and 320/375/768/1024/1440px layout checks.

## Implementation and verification

The component-first gates were completed in order: primitive tests, independent navigation tests, landing/domain component tests, then page assembly and browser QA. Pages only compose the router, shared shell, sections and account workspace. `styles/layout.css` owns the 640px content and 1024px navigation breakpoints; the drawer reads the corresponding CSS token for its desktop reset.

`pnpm --filter @ledger/web test` runs 64 component/hook/page tests. They cover shared validation, stale-read cancellation, filter/page state, exact money, duplicate/uncertain writes, retained references across remount, delayed responses after navigation, and route recovery. A late response clears only its own persisted reference so it cannot erase a newer unresolved intent.

`pnpm test:e2e` runs 19 Chrome/Chromium tests against the real Express API and a disposable PostgreSQL 17 cluster. They cover the landing page and long account/history content at 320/375/768/1024/1440px, both drawer Tab directions, Escape/backdrop/resize/focus restoration, skip link and CTA focus, creation/UUID lookup, credit/debit/rejection flows, copy ID, filtering/pagination, and a response lost after commit followed by an identical-reference retry. Axe checks landing/account screens and the open drawer at representative mobile/desktop widths; these checks are not a complete accessibility certification.

The browser fixture never loads `apps/api/.env`. Explicit global teardown waits for its database to stop and remove its temporary directory before Playwright terminates the server group. See README for browser installation, ports, and startup commands. The configured Supabase database is not mutated by tests.

The transfer follow-up adds 25 independent transfer tests (including actual HTTP timeout classification), one integrated receipt/read-refresh test and one stale-read identity test. Browser coverage adds four real API/database workflows: review/receipt at all five widths with source pagination/filter refresh and destination navigation, lost committed response plus identical retry/conflict, known destination/funds/capacity errors, and retrying failed reads without another POST. Automated axe checks cover successful transfer and conflict states; screenshots were visually reviewed on desktop/mobile. Existing backend contracts, API source, migration files and v0.1 planning are unchanged.

The full regression pass exposed a race in the existing disposable PostgreSQL helper: pg-pool can resolve end() before closing every socket. The helper now tracks client end events and waits before stopping the cluster. This test-infrastructure-only correction does not suppress database errors or alter the production pool/transaction code.

## End-to-end review and account selection (2026-10-28)

`ActiveAccountProvider` owns tab-scoped selected ID/optional known name, without fetching or storing balances. `AccountAccessAction` switches creation to Log out across header/drawer; `ActiveAccountCard` offers My account in landing entry. Selection follows a confirmed creation or verified account read. Logging out clears selection only, leaves pending financial commands untouched, and returns home. Account ID lookup reopens stored data. No login/authentication is implied by this navigation control.

Review fixes: credit/debit fails before sending if retry storage is unavailable; local configuration failure cannot discard an already uncertain credit/transfer; account route case variants share intent storage; receipts match account/type/amount/reference/description; balance/history match requested account/filter/page; invalid descriptions receive focus; deferred route focus does not interrupt a user already typing an Account ID; rejected balance guards refresh reads. Read failures remain distinct from write results, while definitive missing accounts clear stale balance and write controls.

Verification: 390 tests (128 contracts, 180 API, 82 frontend) and 19 browser workflows. New cases cover selection/reload/logout/ID reopen with saved ledger and pending retries, duplicate-name preservation, concurrent balance changes, authoritative missing accounts and response correlation. All five UI widths and automated accessibility checks are included. Tests use disposable local PostgreSQL; this review changes no hosted financial data, API source, contracts or applied migrations.

## Centralized errors (2026-10-28)

ErrorNotice accepts a typed ApplicationError and operation context, resolves all public copy/actions from the shared catalog, and renders only message, code, support ticket ID and one action button. Field controls reference one mapped validation notice rather than repeating raw schema issues. StatusMessage is now reserved for non-error informational/success feedback.

ApplicationErrorBoundary, GlobalErrorHandler and bootstrap fallback handle render, event, async and mount failures. React's diagnostic callbacks suppress default raw console errors. reportError deduplicates by normalized error identity and keeps 50 private original/cause records; console output includes only ticket/code/scope. runSafely handles synchronous exceptions and rejected callbacks. HTTP failures retain server ticket IDs even for non-JSON responses when their header is available; untrusted received copy is never displayed.

Read retries never send financial requests. Unconfirmed account creation offers Go Back; unconfirmed financial writes retry only their saved command/reference. Concurrent balance/history refresh errors use a single notice while retaining a committed receipt and last-confirmed balance. Clear validation errors when input changes, preserve pending-write state and do not claim a conflict proves an earlier result.

Verification: 474 tests (156 contracts, 210 API, 108 frontend) and 24 browser workflows, including hostile received copy, public envelope shape, support IDs, field focus, unknown failures and responsive/automated accessibility checks at all five widths. API/client must be updated together for the new envelope. IDs correlate diagnostics; no external support ticket or telemetry platform is configured.

A later 400/404/422 retry rejection cannot establish the result of an earlier unconfirmed write. Both financial hooks retain the original intent and uncertain state until a correlated success or explicit duplicate conflict is available.

Review follow-up: ErrorNotice registers every displayed ID, including restored intentions, and prevents concurrent recovery callbacks. Metadata includes timestamps and links coalesced read failures; getErrorDiagnostics accepts an ID filter. Combined read failures retain the history panel and use one Retry account action. Transfer storage failures hide the redundant Confirm action. Header/body ID mismatches remain unconfirmed and keep available server correlation. See [support-ID lookup](error-handling.md) for proof and retention limits.

Vite retains its installed secret-file deny rules and additionally blocks logs, test results and Playwright reports over HTTP. A regression check reads the fixture log locally to resolve a displayed ID, then verifies that downloading that same log through the frontend returns 403 without exposing the ID.
